# Design: Черновой технический дизайн ChemSim

> Статус: предварительный. Это гипотезы для обсуждения, а не утверждённая архитектура.

## Предлагаемые слои

- **Presentation (Godot UI):** рабочая область, редакторы веществ/реакций, панель условий, графики и управление временем.
- **Application:** сценарии создания эксперимента, валидации, запуска/паузы/сброса, сохранения/загрузки.
- **Domain:** вещества, компоненты реакций, стехиометрия, параметры кинетики, состояние эксперимента и ограничения модели.
- **Simulation:** независимый от UI вычислительный контур, интегратор ОДУ, шаг времени, события остановки и сбор результатов.
- **Infrastructure:** сериализация проекта, миграции формата сохранения, настройки и экспорт.

## Ключевые проектные вопросы

1. **Область модели.** Для MVP предлагается однородная система реакций в закрытом объёме. Нужна ли только базовая кинетика действующих масс или пользователь должен задавать произвольные кинетические законы?
2. **Состояние.** Для обычных реакций состояние можно представить вектором количеств/концентраций компонентов. Нужно согласовать единицы и объём системы.
3. **Скорость.** Для элементарной реакции вида `aA + bB -> cC` предлагается закон `v = k[A]^a[B]^b` только если это соответствует выбранной модели и порядку реакции. Стехиометрические коэффициенты не всегда равны порядкам реакции; редактор должен разделять эти понятия.
4. **Температура.** Если температурная зависимость включена, потребуется выбрать упрощённую модель Аррениуса и требовать энергию активации либо использовать фиксированную температуру.
5. **Численное решение.** Явный Euler прост, но может быть неустойчив. Для MVP стоит сравнить RK4 с адаптивным решателем; решение принимается после выбора сложности модели и диапазона скоростей.
6. **Графики.** Сбор данных должен быть отделён от частоты отрисовки UI, чтобы график не влиял на физический результат.
7. **Сохранения.** Версионируемый JSON-файл эксперимента с явной схемой и валидацией при загрузке.

## Риски

- Слишком широкая область химии приведёт к ложным ожиданиям научной точности.
- Жёсткие системы ОДУ могут потребовать адаптивного/неявного интегратора.
- Произвольные пользовательские выражения создают риск ошибок, неоднозначностей и небезопасного исполнения; в MVP предпочтительнее структурированный редактор.
- Смешение концентраций, количеств вещества и объёма приведёт к неверным результатам.
